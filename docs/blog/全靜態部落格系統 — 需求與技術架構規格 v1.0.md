# 全靜態部落格系統 — 需求與技術架構規格 v1.0

**文件版本：** 1.0（對應 Foliohaven 1.0.0 的資料與操作契約）

**專案類型：** Static Blog / Static Site Generator

**核心技術：** Node.js、TypeScript、React、Astro、HTML、JSON

**系統定位：** 可由使用者或 AI Agent 修改原始碼、以本機檔案管理內容，透過 SSG 產生完整靜態網站的系統

第一次使用請先讀 [README](../../README.md)，依序完成環境、固定頁面、共用文章版型與網站設定，再開始日常文章管理。本文件供需要查閱資料契約與技術細節的使用者及 AI Agent 參考。

# 1. 專案概述

## 1.1 專案目標

建立一套不依賴 WordPress、PHP 或公開網站動態後端的全靜態部落格系統。

系統以 Node.js 作為本機開發與建置執行環境，以 React 建立網站共用元件及本機管理介面，並透過 Astro Static Site Generation（SSG）產生完整靜態網站。

最終部署的網站僅包含 HTML、CSS、JavaScript、圖片、影音、XML、JSON 及其他必要的靜態資源。

公開網站不需要資料庫、CMS Server、Node.js Runtime、Server-Side Rendering 或執行階段內容 API。

## 1.2 核心目標

| 目標       | 說明                                                                            |
| ---------- | ------------------------------------------------------------------------------- |
| 安全性     | 移除公開網站的動態 CMS、PHP、資料庫及內容管理 API，降低伺服器端攻擊面           |
| 效能       | 主要內容在建置階段完成預渲染，避免執行階段資料查詢及頁面組合                    |
| SEO        | 所有可索引頁面具有完整 HTML、Metadata、Canonical URL 及適當的結構化資料         |
| 開發體驗   | 透過 React 管理元件、文章設定及本機預覽，保留自行或透過 AI 直接編輯檔案的自由度 |
| 可維護性   | 內容、設定、元件與建置邏輯分離，支援 Git 版本控制                               |
| 可移植性   | 內容資料模型與路由規則不依附於特定 SSG 框架                                     |
| 部署獨立性 | 建置流程只產生完整靜態網站，部署機制獨立處理                                    |

## 1.3 設計原則

### Build-Time First

網站的主要內容必須在 Build Time 完成。

文章、分類、Tag、列表、分頁及 SEO Metadata 均需預先產生完整 HTML，不允許在瀏覽器載入後才透過 JavaScript 或 API 組合主要內容。

### File-Based Content

文章及其 Metadata 以本機檔案儲存，不使用內容資料庫。

內容應能獨立於網站框架保存、編輯及版本控制。

### Explicit Configuration

文章的分類、Tag、Slug、SEO 及其他中繼資料由作者明確設定。

系統可以根據既定資料結構執行路由組合、列表聚合及模板套用，但不需要實作內容分析、自動分類或複雜的智慧推導機制。

### Component-Based Architecture

React 負責共用 UI 元件與本機管理介面。

網站元件與管理功能應適當分離，避免將管理程式碼打包進正式網站。

### Minimal Client-Side JavaScript

JavaScript 主要負責搜尋、動畫與互動。

一般網站內容不依賴 JavaScript 才能顯示。文章總覽與搜尋頁的查詢參數狀態為明確例外。

### Deployment-Agnostic Output

建置產物必須是一個可獨立提供靜態服務的目錄，不依賴本機開發環境或特定雲端平台。

# 2. 整體系統架構

## 2.1 架構分層

系統分為六個邏輯層。

| 層級                    | 核心技術         | 主要責任                                      |
| ----------------------- | ---------------- | --------------------------------------------- |
| Runtime Layer           | Node.js          | 執行本機服務、檔案操作、開發工具與建置程序    |
| Content Layer           | HTML、JSON       | 保存文章、分類、Tag、SEO 與網站設定           |
| Core Layer              | TypeScript、Zod  | 資料模型、路由規則、資料驗證及共用內容處理    |
| UI / Management Layer   | React、Vite      | 共用網站元件、本機管理介面與預覽              |
| Static Generation Layer | Astro            | 靜態頁面產生、HTML 預渲染、模板及靜態資源建置 |
| Static Output Layer     | HTML、CSS、JS 等 | 完整網站產物                                  |

所有開發模組可以存在同一個 Repository，不需要分別部署。

## 2.2 Node.js Runtime

Node.js 是本機開發及建置環境的主要執行環境。

主要負責：

- 執行 React Studio 所需的本機服務。
- 讀取、建立、修改及刪除內容檔案。
- 執行 TypeScript Core 的資料處理與驗證。
- 執行 Astro Development Server 和 Build。
- 執行圖片、影音等媒體處理工具。
- 管理本機建置流程。
- 提供本機管理介面所需的檔案操作 API。

Node.js、pnpm 與必要工具採已核對相容的精確版本；版本由根 Dockerfile、`.node-version`、package manifests 與 Lockfile 一起固定。升級時重新核對 engine／peer、原生工具及實際建置，不只確認套件可安裝。

原生環境及 Docker 提供相同的程式修改、Studio、預覽、Build 與測試能力；Docker 內含完整工具鏈。原生環境以 Linux 為支援基準，實際工具與啟動步驟見 [README](../../README.md)。VS Code Dev Container 為選用環境，不是系統前提。

Node.js 不需要部署至正式公開網站。

## 2.3 Content Layer

Content Layer 是文章與網站設定的唯一資料來源。

負責保存：

- Article HTML
- Article Metadata
- Category
- Tag
- Site Configuration
- Media Source 與引用資訊

Content Layer 不依附 React、Astro 或其他 UI Framework。

## 2.4 Core Layer

Core Layer 是全站共用的業務邏輯。

主要負責：

| 模組               | 責任                                                  |
| ------------------ | ----------------------------------------------------- |
| Content Model      | Article、Category、Tag、Site Configuration 的資料定義 |
| Schema Validation  | 驗證 Metadata、分類、標籤、日期等資料                 |
| Routing            | 定義及產生所有網站 URL                                |
| Content Loader     | 讀取 HTML、JSON 與網站設定                            |
| Taxonomy           | 管理 Category 階層及 Tag 與文章的關係                 |
| Pagination         | 文章列表排序、分頁與資料集合處理                      |
| TOC Parser         | 從 HTML Heading 建立文章目錄資料                      |
| SEO Model          | 定義及整理各頁面需要的 SEO Metadata                   |
| Search Index       | 建立前端搜尋需要的文章索引                            |
| Content Validation | 檢查資料完整性、路由衝突及文章內容問題                |

**Core Layer 負責定義 URL 規則，Astro 負責依照規則產生靜態頁面。**

同一套 Core 可以被 React Studio、Node.js Local Service 及 Astro Build 共用。

## 2.5 React Layer

React 負責網站 UI 元件與本機內容管理。

包含兩個主要部分。

**Shared UI Components**

管理正式網站與本機預覽可重用的展示元件，例如：

- Header、Footer、Navigation
- Article Header、Article Card
- Category、Tag 元件
- Breadcrumb
- Table of Contents
- Pagination
- Search UI
- 其他展示及互動元件

**React Studio**

提供網站作者使用的本機管理介面，包括：

- HTML 文章編輯
- 即時預覽
- Article Metadata 編輯
- Category / Tag 管理
- SEO 設定
- 媒體管理
- 本機 Build 操作

React Studio 不屬於公開網站。

## 2.6 Astro SSG Layer

Astro 負責將 Content、Core 資料及 UI 元件轉換為最終靜態網站。

主要職責：

- 建立靜態頁面模板。
- 根據 Core 提供的路由資料列舉需要輸出的頁面。
- 在 Build Time 渲染 React 展示元件。
- 將文章 HTML 注入文章模板。
- 預渲染首頁、文章、分類、Tag 與列表分頁。
- 產生 SEO Metadata 與其他 HTML Head 資訊。
- 輸出 CSS、JavaScript 及靜態資源。
- 配合 Sitemap、RSS 等建置工具產生輔助檔案。

Astro 的 File-Based Routing 是 SSG 的實作機制，不是整套系統路由規則的唯一來源。

## 2.7 Static Output Layer

Build 完成後產生獨立的 `dist/` 目錄。

此目錄不包含：

- React Studio
- Node.js Local Service
- 本機管理 API
- 原始文章 Metadata
- Build Scripts
- 內容資料庫
- SSR Server

部署環境只需要能正確提供靜態資源及處理 HTTP 請求。

# 4. 內容儲存與資料模型

## 4.1 來源與共通契約

一篇文章保存在 `content/articles/<articleId>/content.html` 與 `meta.json`。articleId 是單層目錄識別，與公開 slug 分開；1–80 字元 lowercase kebab-case，Studio 使用 `article-<UUID>`。JSON 不再重複保存 id 或正文。

Schema 與型別唯一來源為 `packages/core/src/schemas/`、`models/`；純運算由 `@foliohaven/core` 公開，檔案載入與固定頁核對才由 `@foliohaven/core/node` 公開。禁止跨套件直接匯入 src。

- 來源／API 使用 UTF-8，正文使用 LF，CRLF／CR／NUL 拒絕；正文保留作者原文，不自動格式化。
- 物件使用 strict schema，未知欄位、錯誤型別與超長拒絕；不隱含將字串轉數字。`null` 只適用明列可空欄位，表示未設定。
- 日期必須有 `Z` 或明確 offset，真實年月日／時間，最多毫秒三位小數；超出精度拒絕，不截斷。來源保存作者輸入字串，內部比較 UTC instant，API 日期輸出 UTC `Z`，畫面依網站 timeZone 顯示。
- GET／Build 的預設正規化不回寫來源，保存及 Build 不暗中更新日期。
- meta 每篇最多 64 KiB、HTML 5 MiB；Site／固定頁 JSON 每檔 256 KiB，categories／tags 各 4 MiB，media meta 16 KiB。限制皆計 UTF-8 bytes，文章最多 10,000 篇、published 正文累計 256 MiB；超限不截斷資料。
- 只讀一般檔案；拒絕 symlink、穿越、越界 realpath 與額外文章巢狀目錄。不把 API 輸入當作任意檔案路徑。

## 4.2 Article Metadata

載入後 Article 由 `{articleId,contentHtml,meta}` 組成；`meta.json` 固定欄位如下。

| 欄位                   | Draft／預設                    | Published                              |
| ---------------------- | ------------------------------ | -------------------------------------- |
| status                 | 必填 `draft`                   | 必填 `published`                       |
| title                  | string，預設 `""`，最多 200    | trim 後 1–200 字元                     |
| slug                   | string，預設 `""`，最多 80     | 合法且非純數字的 lowercase kebab-case  |
| category               | string 或 null，預設 null      | 既有完整分類 path，最多 512 字元       |
| tags                   | 預設 []，最多 20、不重複       | 全部為既有 Tag slug；[] 合法           |
| publishedAt／updatedAt | 有效日期或 null，預設 null     | 皆必填，更新不得早於發布               |
| featuredImage          | 受管圖片路徑或 null，預設 null | 有值時必須能處理輸出                   |
| featuredImageAlt       | string，最多 300，預設 `""`    | 有精選圖必須明確提供，裝飾圖可用空字串 |
| seo                    | 下節覆寫物件，省略時正規化     | 依單筆／頁型／全域解析有效描述               |

Draft 可以保存未完成正文、slug、分類關聯、Heading 或媒體引用，回傳診斷；型別、未知欄位、日期及容量錯誤仍拒絕。Published 必須滿足全部發布規則。合法 draft 在正式 Loader 解析 meta 後排除，不讀其未完成正文；壞 JSON、未知 status、缺 meta 仍使 Build 失敗，不能假裝成草稿。

status 是唯一發布開關；未來日期只列 warning，不排程發布。published＋noindex 仍是公開文章，只排除 Sitemap；draft 完全不進公開 HTML、列表、RSS、搜尋、Sitemap 及 draft-only 媒體閉包。

文章另有 `excerpt`（trim、最多300字元，預設空字串）與 `relatedReading:{title,articleIds}`（最多20個唯一已發布文章ID，不可自我／缺失／草稿引用）。ViewModel提供有效description與有序延伸閱讀卡片；刪除被引用文章回409。

## 4.3 SEO 覆寫物件

文章、分類、Tag 與固定頁共用：

```json
{
  "title": null,
  "description": null,
  "index": null,
  "ogImage": null
}
```

| 欄位        | 型別與用途                                                                    |
| ----------- | ----------------------------------------------------------------------------- |
| title       | 1–200 字元或 null；有值時直接作為 SEO 標題，null 將內容標題套用頁型或全站 titleTemplate |
| description | 1–300 字元或 null；逐欄繼承頁型／全域，文章不再強制每篇單填 |
| index       | boolean 或 null；null 繼承頁型再繼承 defaultSEO.index；false 是明確設定     |
| ogImage     | 受管圖片公開路徑或 null；配合 imageSource 的 inherit/custom/none 及頁型 featured 規則           |

`imageSource` 可省略，或為 inherit／custom／none；custom 必須提供 ogImage，none 明確關閉圖片。舊資料非空 ogImage 仍視為 custom。全站 pageSEO 的文章頁型另可用 featured。各欄獨立採單筆→頁型→全域；八頁型為 home/article/articles/categoryIndex/category/tagIndex/tag/notFound，解析後保留 sources/sourceLayers。

不接受任意 canonical、robots 字串、Twitter 物件等未知欄位。這是作者的覆寫資料，不是完整輸出 SEO；正式 SeoViewModel 與 HTML 見第 12 節。

## 4.4 Article HTML 與完整範例

正文為 HTML fragment，不含 Document 或 H1；H1 由共用 ArticlePage 根據 title 輸出。H2–H6 必須有非空、唯一、無空白的 id，不得使用 `ui-` 前綴；Core 只以 H2／H3 產生 TOC。層級跳級列 warning。站內連結用根路徑／fragment，媒體用受管公開路徑。

```html
<p>這是一篇筆記。</p>
<h2 id="preparation">準備內容</h2>
<p>使用 HTML 保存正文，JSON 保存屬性。</p>
<h3 id="files">必要檔案</h3>
<p><a href="#preparation">回到準備內容</a></p>
```

以下完整 metadata 使用正式範例已有的 `notes`／`example`，無圖片相依：

```json
{
  "status": "published",
  "title": "我的第一篇筆記",
  "slug": "my-first-note",
  "category": "notes",
  "tags": ["example"],
  "publishedAt": "2026-10-23T09:00:00+08:00",
  "updatedAt": "2026-10-23T09:00:00+08:00",
  "featuredImage": null,
  "featuredImageAlt": "",
  "seo": {
    "title": null,
    "description": "示範以 HTML 與 JSON 建立文章，完成預覽、發布與靜態建置。",
    "index": null,
    "ogImage": null
  }
}
```

新增文章不改 React／Astro，URL 為 `/notes/my-first-note/`。API 寫入為 `{contentHtml,meta}`；讀取資源為 `{id,contentHtml,meta,diagnostics}`，禁止將 id／diagnostics 回寫為 metadata。

# 5. Category 與 Tag

## 5.1 Category 結構

Category 是階層式樹狀結構，支援多層分類。

任何分類節點都能直接包含文章，不限於葉節點。

例如：

```text
Others
├── Article 1
├── Cloudflare
│   ├── Article 2
│   └── Article 3
└── Linux
    └── Article 4
```

對應文章路徑：

```text
/others/article-1/
/others/cloudflare/article-2/
/others/cloudflare/article-3/
/others/linux/article-4/
```

Category 規則：

1. 一篇文章只能指定一個 Category。
2. Category 在完整 path 最多 512 字元的界線內支援多層子分類。
3. 父分類可以直接包含文章。
4. 文章使用完整 Category Path。
5. Category 階層由明確設定的資料結構決定。
6. 系統不自動推測文章應該歸屬的分類。
7. 父分類頁面包含自身及所有下層分類的已發布文章。
8. 聚合列表不得重複顯示同一篇文章。

例如 `/category/others/` 會包含 Article 1、2、3、4。

`/category/others/cloudflare/` 只包含 Cloudflare 分類及其下層分類的文章。

## 5.2 Category Model

| 欄位        | 說明                       |
| ----------- | -------------------------- |
| path        | 完整分類路徑，作為唯一識別 |
| name        | 分類顯示名稱               |
| description | 分類描述                   |
| seo         | 可選的 SEO 模板覆寫資訊    |

分類資料固定由 `content/categories.json` 的陣列集中管理。

例如：

```json
[
  {
    "path": "others",
    "name": "Others",
    "description": "Other technical topics."
  },
  {
    "path": "others/cloudflare",
    "name": "Cloudflare",
    "description": "Cloudflare-related articles."
  },
  {
    "path": "others/linux",
    "name": "Linux",
    "description": "Linux-related articles."
  }
]
```

父子關係由完整分類路徑表達，Core 負責驗證路徑合法性及上層分類是否存在。name 為1–120字元、description為1–300字元且非空；seo省略時補第4節預設，未知欄位拒絕。

顯示名稱／描述可直接修改；有子分類、任一 draft／published 或導覽引用的分類不得直接刪除。path／Tag slug 改名須先預覽 migration 影響，再以可復原交易同步定義、子分類、文章及導覽結構化引用。正文不自動改寫，舊站內連結必須由作者修正；不產生自動 redirect。

## 5.3 Tag 結構

Tag 採用扁平結構，不存在父子關係。

文章可以具有零至多個 Tag。

Tag 不影響文章 URL。

Tag Model：

| 欄位        | 說明                    |
| ----------- | ----------------------- |
| slug        | Tag 唯一識別            |
| name        | 顯示名稱                |
| description | Tag 描述                |
| seo         | 可選的 SEO 模板覆寫資訊 |

Tag 由 `tags.json` 集中管理。

每個 Tag 具有獨立公開頁面，列出所有指定該 Tag 的已發布文章。

## 5.4 命名規範

Category 和 Tag 的顯示名稱與 Slug 獨立保存。

### 顯示名稱

英文使用一般的 Title Case 命名風格，專有名詞及縮寫保留正式大小寫。

例如：

| Name                 | Slug                 |
| -------------------- | -------------------- |
| Others               | others               |
| Cloudflare           | cloudflare           |
| Web Performance      | web-performance      |
| JavaScript           | javascript           |
| Frontend Development | frontend-development |
| SEO                  | seo                  |

中文顯示名稱不強制轉換成英文。

### Slug

統一使用 lowercase kebab-case。

規則：

- 允許小寫英文字母、數字及連字號。
- 英文單字之間使用 `-`。
- 不使用空白、底線或大寫字母。
- 不允許空字串。
- 不使用純數字 Slug，以避免與數字分頁路由衝突。
- 同一 URL 命名空間中的完整路徑必須唯一。
- Slug 與顯示名稱不需同步修改。

Slug 由作者明確設定，不自動生成。

# 6. Site Configuration 與固定頁

## 6.1 全站設定

`content/site.json` 為全站唯一設定；UI／Studio／Astro 不另存副本。

| 欄位                      | 正式契約                                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| siteName／siteDescription | 必填非空，分別最多 120／300 字元                                                                                                                              |
| siteUrl                   | HTTP(S) origin，以 `/` 結尾，無帳密、子路徑、query、fragment；目前範例 `https://example.invalid/`                                                             |
| language／timeZone        | 有效 BCP 47／IANA 名稱，預設 zh-Hant／Asia/Taipei                                                                                                             |
| author                    | 必填 `{name,url}`，name 非空最多 120，url 為 HTTP(S) 或 null                                                                                                  |
| navigation                | 最多 20 個 `{label,href}`；label 1–80，href 為有效站內已登錄 URL 或 HTTP(S)                                                                                   |
| defaultSEO                | `{titleTemplate,description,index}`；template 只接受 `{title}`、`{siteName}`，預設 `{title} \| {siteName}`；description 回退 siteDescription，index 預設 true |
| pagination                | `{category,tag,articles}` 各為 1–100 整數，預設 10；五篇範例明確為 2                                                                                          |
| home                      | `{featuredArticleIds,featuredCaption,latestCount}`；最多 20 個唯一且已發布 ID，latestCount 1–20                                                                               |
| rss                       | `{title,description,maxItems}`；前兩者回退站名／說明，maxItems 1–10000，預設 100                                                                              |
| social                    | `{defaultImage,twitterSite}`；受管圖片或 null、合法 `@` 帳號或 null                                                                                           |
| googleSiteVerification    | 非空最多 512 字元或 null；只在首頁輸出，null 不產生 tag                                                                                                       |

未知欄位／placeholder、非法網址／時區、未知導覽、無效首頁精選或媒體引用皆明確失敗，不回退成空站。空 categories／tags／articles 合法，設定檔缺失不是空集合。

新增 `favicon`、`icons` 與 `pageSEO`：圖示可輸出ICO／SVG／PNG、多尺寸瀏覽器圖示、Apple Touch Icon、Safari mask icon、theme-color與條件式site.webmanifest。各平台可停用；不包含Service Worker／離線能力。

`pageSEO` 分為 home、article、articles、categoryIndex、category、tagIndex、tag、notFound 八種頁型，每種可設定 `titleTemplate`、`descriptionSource`、`description`、`index`、`imageSource` 與 `ogImage`。`descriptionSource` 使用 inherit／custom／content，其中 content 只適用首頁、文章、分類與 Tag；文章使用摘要作為內容描述。`imageSource` 使用 inherit／custom／none，文章頁型另可用 featured；沒有精選圖時回退全站分享圖。單筆覆寫優先於頁型，各欄獨立解析，不把 false 或 none 當成未設定。

## 6.2 固定頁唯一登錄

`site/src/fixed-pages.ts` 的 `fixedPages` 保存 `{id,path,entry,seo,mediaRefs}`，目前有 home `/`、articles `/articles/`、category-index `/category/` 與 tag-index `/tag/`。entry 相對 site，例如 `src/pages/about/index.astro`；seo 使用第 4 節覆寫；mediaRefs 明列固定頁／共用 UI 使用的受管媒體。

每個固定頁必須具備 React 主體、UI 公開 export、Astro Entry 與登錄。Core 合併固定／文章／分類／Tag 路由，Node adapter 核對實體 Entry 及 URL，拒絕未登錄固定頁、缺檔、碰撞、symlink、Astro 忽略的隱藏／底線入口；動態 Entry、輔助 endpoint 與 404 明列例外。

登錄以獨立 NodeNext 專案編譯，由 `@foliohaven/site/registry` 公開，private output 在 `site/dist/registry/`，不進公開 dist。服務／CLI／snapshot 使用相同 registry，不跨 package 讀 src。

固定頁專用資料可保存 `content/pages/<pageId>.json`；pageId 為 1–80 字元 lowercase kebab-case，每檔最多 256 KiB。每頁必須在同檔 `pageSchemas` 登錄 strict Zod schema；未登錄 JSON 拒絕。沒有設定需求可直接以 React JSX 維護，不強迫建立 JSON。

Astro 入口使用 `site/src/lib/server/context.ts` 的 `loadFixedPage(id)` 取得 `{site,seo,data}`；內容已由本輪快照驗證產生，不在頁面重讀 live content。完整可執行範例見[一般獨立頁面建立流程](一般獨立頁面建立流程.md)。

# 7. 網站資訊架構與路由

## 7.1 路由責任

網站路由分成三個職責：

| 責任                                 | 所屬模組        |
| ------------------------------------ | --------------- |
| URL 規則與組合                       | TypeScript Core |
| 靜態頁面路由列舉與產生               | Astro SSG       |
| 正式環境 HTTP URL 解析及靜態檔案服務 | 部署環境        |

Core 提供共用 Routing Functions，負責根據 Article、Category、Tag 及分頁資訊產生正式 URL。

Astro 透過這些資料產生靜態頁面。

## 7.2 頁面類型

| 頁面           | URL                             | 內容               |
| -------------- | ------------------------------- | ------------------ |
| 首頁           | `/`                             | 網站入口與主要導覽 |
| 文章頁         | `/others/article-1/`            | 完整文章           |
| 子分類文章     | `/others/cloudflare/article-2/` | 完整文章           |
| 分類頁         | `/category/others/`             | 分類文章列表       |
| 子分類頁       | `/category/others/cloudflare/`  | 子分類文章列表     |
| 分類分頁       | `/category/others/2/`           | 分類第二頁         |
| Tag 頁         | `/tag/security/`                | Tag 文章列表       |
| Tag 分頁       | `/tag/security/2/`              | Tag 第二頁         |
| 文章總覽／搜尋 | `/articles/`                    | 全部文章及前端搜尋 |

首頁主要提供網站資訊、導覽、分類入口及精選文章等內容。

首頁不提供分頁。

## 7.3 文章 URL

文章 URL 格式：

```text
/{category-path}/{article-slug}/
```

例如：

```text
/others/cloudflare/deploy-static-blog/
```

文章 URL 依明確指定的 Category Path 與 Article Slug 組合。

## 7.4 Category URL

分類頁使用 `/category/` 作為固定前綴：

```text
/category/others/
/category/others/cloudflare/
```

## 7.5 Tag URL

Tag 頁使用 `/tag/` 作為固定前綴：

```text
/tag/cloudflare/
/tag/web-performance/
```

## 7.6 URL 格式規範

**所有 HTML 頁面網址均以 `/` 結尾。**

例如：

```text
/
/others/article-1/
/category/others/
/tag/cloudflare/
/articles/
```

其他資源保留檔名及副檔名，不附加結尾斜線（UUID 代表實際媒體識別）：

```text
/assets/main.css
/assets/main.js
/media/<UUID>/image.webp
/media/<UUID>/video.webm
/rss.xml
/search-index.json
/robots.txt
```

Astro 採用 Static Output 與 Directory Build Format。

```js
export default defineConfig({
  output: 'static',
  trailingSlash: 'always',
  build: {
    format: 'directory',
  },
});
```

因此文章：

```text
/others/article-1/
```

對應實際輸出：

```text
dist/others/article-1/index.html
```

Build 必須檢查完整 URL 衝突，並保留 `category`、`tag`、`articles` 等系統根路徑。

本系統輸出尾斜線 canonical 與目錄式 HTML；交付範圍止於 dist，不加入遠端 URL 轉址或服務設定。

# 8. 列表與分頁

## 8.1 Category 分頁

Category 頁必須支援分頁。

第一頁使用分類本身的網址，不建立 `/1/`。

例如：

```text
/category/others/
/category/others/2/
/category/others/3/
```

子分類分頁：

```text
/category/others/cloudflare/
/category/others/cloudflare/2/
```

所有分類分頁在 Build Time 產生完整 HTML。

## 8.2 Tag 分頁

Tag 頁採用相同規則：

```text
/tag/security/
/tag/security/2/
/tag/security/3/
```

各分頁具備獨立 URL、預渲染文章列表、SEO Metadata 及 Canonical URL。

分頁連結必須使用正常 HTML Anchor，不能依賴 JavaScript 才能前往下一頁。

## 8.3 列表排序與資料處理

列表依 `publishedAt` 的 UTC instant 由新到舊排序。

相同 UTC 發布時間固定以 articleId ASCII 升冪次排序，避免依語系或檔案列舉順序改變結果。

每頁文章數量由 Site Configuration 管理。

列表聚合時應排除草稿，並避免重複文章。

超出有效範圍的 Category / Tag 分頁不產生靜態頁面。

# 9. 全部文章與搜尋系統

## 9.1 整合頁面

全部文章列表與搜尋整合為同一個頁面：

```text
/articles/
```

不另行建立獨立搜尋頁面。

透過 Query Parameters 管理搜尋與分頁狀態。

| URL                              | 行為           |
| -------------------------------- | -------------- |
| `/articles/`                     | 全部文章第一頁 |
| `/articles/?page=2`              | 全部文章第二頁 |
| `/articles/?q=cloudflare`        | 搜尋結果第一頁 |
| `/articles/?q=cloudflare&page=2` | 搜尋結果第二頁 |

參數規則：

- `q`：搜尋關鍵字。
- `category`：可重複指定分類 path，包含各分類的後代。
- `tag`：可重複指定 Tag slug。
- `page`：頁碼。
- 未指定 `q` 及篩選時顯示全部文章；可只使用分類或 Tag 篩選。
- 未指定 `page` 時顯示第一頁。
- 第一頁不需要 `page=1`。
- 搜尋或換頁時更新 URL。
- URL 可直接複製與分享。
- 搜尋關鍵字改變時重設至第一頁。
- 無效頁碼或沒有搜尋結果時顯示適當的空狀態。

## 9.2 靜態搜尋索引

Build Time 產生靜態搜尋索引，例如：

```text
/search-index.json
```

索引包含：

- Title
- URL
- Slug
- Category
- Tags
- Description / Excerpt
- Published At
- Updated At
- Featured Image

前端 JavaScript 讀取靜態索引並在瀏覽器中搜尋。

公開搜尋僅比對 title、Category path／name、Tag slug／name、description，不比對文章 slug 或正文。q 做 NFKC、trim、合併空白與小寫正規化，最多 200 字元，以空白分詞 OR 比對；命中詞數多者優先，再依發布時間降冪及 articleId ASCII 升冪排序。同一組分類或 Tag 選項使用 OR，分類與 Tag 兩組之間以及與關鍵字結果之間使用 AND。切換條件重設第一頁，URL 與返回／前進會保留選項。Studio 文章管理搜尋則沿用管理集合的 AND 比對，不與公開搜尋規則混用。

不需要後端搜尋服務或動態內容 API。

## 9.3 渲染與分頁行為

`/articles/` 的初始 HTML 必須包含完整的第一頁文章列表，不能是空白容器。

索引下載上限64 MiB、15秒，UTF-8／schema／version錯誤明確拒絕；載入失敗保留 SSG 第一頁並提供重試。初次 hydration 必須先與 SSG 第一頁一致，完成後才套用 query，避免 hydration mismatch。

JavaScript 載入後：

1. 讀取 URL Query Parameters。
2. 載入靜態搜尋索引。
3. 執行搜尋、排序或分頁。
4. 更新文章卡片及分頁介面。
5. 維護瀏覽器 URL 與上一頁／下一頁的瀏覽歷史行為。

**此頁是唯一允許由 JavaScript 根據資料組合主要列表內容的頁面。**

## 9.4 SEO 限制

由於純靜態伺服器不會因為 Query Parameters 不同就自動回傳不同 HTML，`/articles/?page=2` 等網址與 `/articles/` 共用相同的初始 HTML。

因此：

- `/articles/` 是主要可索引入口。
- Query Parameter 狀態不產生獨立 HTML。
- 查詢參數變體不列入 Sitemap。
- 初始 HTML 使用 `/articles/` 作為 Canonical。
- 不把搜尋狀態當作獨立的 SEO Landing Page。
- 不要求搜尋引擎索引各個查詢參數頁面。

此處的 Query Parameter 分頁屬於前端互動功能，不等同於 Category / Tag 的靜態 SEO 分頁。

停用 JavaScript 時，頁面可顯示預渲染的預設文章列表，但無法還原指定查詢參數對應的搜尋結果。

文章的搜尋引擎可發現性主要由文章頁、Category、Tag、Sitemap 及一般 HTML 連結提供。

# 10. 文章目錄（TOC）

文章頁必須支援 Table of Contents。

TOC 直接根據 `content.html` 的 Heading 產生，不獨立建立 TOC Metadata。

## 10.1 產生方式

文章內容：

```html
<h2 id="introduction">Introduction</h2>
<p>...</p>

<h2 id="installation">Installation</h2>
<p>...</p>

<h3 id="configuration">Configuration</h3>
<p>...</p>
```

Build Time 解析 Heading，產生：

```text
Introduction
Installation
└── Configuration
```

## 10.2 TOC 規則

- H1 由 Article Template 產生，不納入 TOC。
- 正式 TOC 收錄 H2、H3；H2–H6 全部必須有合法且唯一的 id。
- TOC 文字由 Heading 的文字內容取得。
- Anchor 使用 Heading 既有的 `id`。
- Heading ID 由作者在 HTML 中設定。
- 不另外儲存 Heading 或 Anchor 資料。
- Build 時檢查 Heading ID 是否缺失或重複。
- TOC 在 Build Time 輸出完整 HTML。

JavaScript 可以處理：

- 目前閱讀章節標示。
- 平滑捲動。
- TOC 展開與收合。
- 其他閱讀互動。

TOC 的基本內容及連結不能依賴 JavaScript 才出現。

# 11. React Studio、API 與本機保存

## 11.1 操作入口與模式

Studio 是網站作者使用的本機工作室，不是公開 CMS，不提供多使用者登入／角色。Docker app 或原生 `pnpm start` 提供來源預覽 `4321`、Studio `5173`、成功網站預覽 `4322`；API 只經 Studio 同源 proxy 使用。也可使用根目錄 `pnpm dev` 啟動 package watch、Astro、Studio 及 Local Service，再另開終端執行 `pnpm preview`。原生直接開啟 localhost 網址，Docker 使用主機對應連接埠；選用 Dev Container 時才需編輯器轉送。同一工作區一次只啟動一組作者服務。

Studio 畫面為文章、分類與 Tag、全站設定、媒體庫、Build 與工作、衝突與復原。編輯器使用 CodeMirror，明確保存／Ctrl/Cmd+S；300 ms debounce 預覽，取消過時請求並只採最新序號。離開 dirty 編輯時提醒；保存成功才更新載入版本。

工作區 editMode 預設 studio；改用 IDE 保存前切 ide，Studio 來源 mutation 回 409，讀取／檢查／預覽可用。IDE 模式不禁止 CLI Build；切回 studio 重新掃描診斷，作者重新載入。模式／復原決議可在阻擋狀態操作；未解復原禁止一般來源 mutation 及 Build。同 UID 的 IDE 不受服務鎖約束，不能宣稱模式會技術阻止外部保存。

新文章 POST 只接受 draft；先建立草稿再發布。編輯器發布／撤回使用目前完整候選一次 PUT，不只切換磁碟舊稿的 status；列表快捷發布才使用 publication PATCH。保存、發布、刪除都不直接更新 dist，須再成功 Build。

管理清單回傳結構合法、但有 HTML／路由／媒體語意錯誤的 ArticleResource 與 Core 真實 diagnostics，作者可開啟修復；壞 JSON、未知 status、缺配對或超限仍422，symlink 依既有安全契約回409；都不能吞成空集合。分類遷移保留正文舊連結後，亦可從清單逐篇修正。

Published 候選保存於同 writer tracking session 比較 Core 產生的前後 diagnostics：本篇所有 error 及無法明確歸屬文章的 global error 一律拒絕；只允許未修改的其他文章既有 error 原樣存續。identity 含 severity、code、message、articleId、resource、field、line、column，保留出現次數，不能只比 code；新增／改變他篇 error 或增加次數均拒絕。其他來源／清單仍受 raw dependency 最後檢查，避免外部改動混入豁免。此規則只讓作者逐篇修復，不改正式 Build 的全站零 error 標準。

## 11.2 HTTP 共通契約

前綴 `/api/v1`，JSON UTF-8、成功回資源本體，管理回應 no-store 與 X-Request-Id。集合預設 page=1／pageSize=20，上限 100；Core 管理篩選／排序／分頁，ID 穩定次排序。日期回 UTC `Z`。

JSON body 上限 32 MiB，解碼後仍套正文／metadata 各自限制；header 16 KiB。JSON timeout 15 秒、預覽 10 秒；上傳最多 15 分鐘、無資料 30 秒中止。錯誤固定 `{error:{code,message,requestId,retryable,issues?}}`，不含 stack、絕對路徑、命令、token 或任意原始 stderr。

| 狀態          | 語意                                                  |
| ------------- | ----------------------------------------------------- |
| 400／405／415 | 無效請求／不支援方法（附 Allow）／Content-Type 不支援 |
| 403           | Host、Origin 或 proxy 驗證失敗                        |
| 404           | 資源不存在或預覽過期                                  |
| 408／413／431 | 逾時／body 太大／header 太大                          |
| 409           | 模式、引用、工作、復原或冪等衝突                      |
| 412／428      | If-Match 已過期（回最新 ETag）／缺 If-Match           |
| 422           | Schema、發布規則、格式或容量檢查失敗                  |
| 429           | queued＋running 已達 20，附 Retry-After               |
| 500／503      | 內部錯誤／必要元件不可用                              |

## 11.3 資源介面

下表 URL 相對 `/api/v1`；PUT 是完整替換，僅 PATCH publication 表列欄位。共通限制、版本／冪等與持久工作分別見11.2、11.4及11.5；嚴格資料型別以 `packages/core/src/schemas/` 的公開契約為準。

| Method／資源                             | 輸入與結果                                                                                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |

## 11.4 強版本、冪等與來源交易

- 來源 raw bytes 用 SHA-256 revision；文章與媒體 HTTP 強 ETag 另涵蓋實際 DTO，包括 diagnostics／asset。同 ETag 不可回不同 representation；derived 資料改變即更新 tag。workspace ETag 另涵蓋模式與來源／產物復原狀態，與來源 revision 分開。
- 已有來源／設定／模式／復原 mutation 要精確單一 strong If-Match，不接受 `*`／weak tag；在同 writer session 重算目前表示後比較，仍保留 raw revision 與跨資源最後檢查。412 保留原載入／目前磁碟／未保存三版本，不盲目覆蓋。
- 建立文章、媒體及工作先 durable reservation，Idempotency-Key 為 UUID；operation kind＋canonical semantic payload hash 防跨端點重用。同 key 執行中 409 附 operationId；完成同 payload 於 7 天內重送原 status／body／ETag／Location，異 payload 409。GET 才讀最新狀態。Job 原 202 固定為建立當時 queued 快照，不隨完成重寫。
- repository 使用固定 inode 的 kernel flock 與單 writer queue，一致讀者不看半套 HTML／JSON；保存先寫 prepared／獨立 backup／journal 並 fsync，再核對 raw hash、以 exclusive 安裝避免覆蓋外部新增，最後 durable committed 才回成功。不是宣稱多檔一次 rename 原子完成。
- 未知外部版完整保留為 recovery-required，不強蓋；來源／dist 復原 detail 含 base、current、prepared、額外 preserved。revisions 為全部 `{resourceKey,revision}`，不存在為 null；選擇依 detail choices，不把資源 key 當任意 path。

成功歷史及 trash 為 available，可比較／還原，不阻工作區；未知未解為 pending，處理後 resolved。resolution 持久 intent 及子交易連結，自身中斷也可復原。成功備份至少 7 天且最近 20 筆，未解不自動清理；trash 保存 30 天，永久 purge 另行明確確認且無未解引用。還原 trash 目標有任何同名新資料均 409。

## 11.5 持久工作與安全邊界

Job type 為 build／media／taxonomy；狀態 queued／running／succeeded／failed／cancelled／interrupted，progress `{completed,total}` 未知 total 用 null。queued＋running 合計上限 20。build 同時一個、image 兩個、video 一個，皆跨程序 lease，不只程序內旗標。

成功終態的已知總量須在同一次Job保存中收尾為completed=total，涵蓋正常完成及依durable proof恢復；不得在產物／來源提交完成前提前報滿，也不得為進度更新改變artifact／jobs-state鎖順序。failed／cancelled／interrupted與執行中保留最後實際進度；total=null不製造總量、total=0不除零。既有succeeded但進度未收尾的紀錄維持可讀，get／list以成功狀態投影完整已知進度，不重寫原歷史JSON或原202冪等回應。Studio成功階段顯示「已完成」，未知／零總量的成功亦顯示完成；其他終態未知總量顯示未提供進度，不持續宣稱估計中。

重啟先復原：running 有 artifact／media immutable receipt／taxonomy 同 journal completion proof 才回 succeeded，無證據記 interrupted；queued 先核對原來源版本。重試建立新 job，retryOf 只指同 type failed／cancelled／interrupted；不自動重做未知副作用。

取消先持久單向 flag 並 abort，等待真正 worker／FFmpeg close 後結束；已提交產物不回滾，晚取消 409 並維持 succeeded。Build 全程上限 3 小時；依賴／render 各 15 分鐘，媒體依各 worker deadline。

Local Service 固定 loopback，proxy 以 x-alfred-process-token 驗證，mutation 的 Origin 必須精確等於 x-alfred-studio-origin 所描述的觀察來源。proxy 覆寫這兩個 header；token 僅 Node IPC 記憶體傳遞，不進 browser、VITE_、檔案或 log。無任意 CORS、任意命令、任意檔案讀取或遠端 URL 抓取。

預覽 iframe 無 allow-scripts／allow-same-origin，CSP 只允許共用 CSS 及受控媒體，隔離不改寫保存原文。Vite fs allowlist 排除 content、media/source、server、.alfred、.git、機密及 Node-only 輸出。

# 12. SEO 架構

## 12.1 作者資料與正式輸出分工

作者保存第 4 節的 `{title,description,index,ogImage,imageSource?}` 覆寫，以及全站 `pageSEO` 設定。Core `resolveSeo` 產生完整 `SeoViewModel`，Astro `site/src/components/SeoHead.astro` 統一輸出；React／Astro 不另計 canonical 或繼承規則。首頁、文章、文章總覽／搜尋、分類總覽、分類頁、Tag 總覽、Tag 頁及 404 分別套用八種頁型；其他自訂固定頁使用單筆覆寫及全站預設。

## 12.2 初始 HTML 的資訊

| 輸出               | 正式行為                                                                           |
| ------------------ | ---------------------------------------------------------------------------------- |
| `<html lang>`      | site.language，由 BaseLayout 輸出                                                  |
| title／description | 單筆覆寫→頁型設定（可採內容描述／模板）→全站回退；分頁第二頁起標題加頁碼 |

SEO 已存在初始 HTML，不依賴客戶端 JavaScript。圖片不存在時省略相關 image tag，不輸出假 URL；圖片文字不另由 SEO 推測。

## 12.3 Canonical、索引與分頁

文章、固定頁、分類／Tag 各靜態分頁都有自己的正式 canonical，例如 `/category/notes/` 與 `/category/notes/2/`。`/articles/?q=...&page=2` 只為瀏覽器查詢狀態，共用 `/articles/` 的初始 HTML 與 canonical，不生成獨立 SEO 頁。

index 依序使用單筆 seo.index、頁型 pageSEO.index、全站 defaultSEO.index，null 才向下繼承。noindex 的 published 文章仍輸出 HTML、列表、RSS、搜尋，只排除 Sitemap；draft 完全隔離。全站 noindex 在沒有單筆或頁型覆寫時生效；空分類／Tag、404 與預覽另有強制 noindex 規則。

## 12.4 Structured Data

文章 BlogPosting 含 headline、description、可用 image、author Person name／可選 url、UTC datePublished／dateModified、mainEntityOfPage。BreadcrumbList 依 Core 導覽產生 itemListElement、position、name、absolute item URL。固定頁不冒用文章 BlogPosting。

JSON-LD 以 Core `serializeJsonLd` 安全序列化，避免文字中的 `<` 等字元突破 script 容器；不將作者任意 JSON 當可執行 script 注入。

## 12.5 輔助檔

`@astrojs/sitemap` 只收 route manifest 中可索引頁面，產生 `/sitemap-index.xml` 與必要 `/sitemap-<n>.xml`。Draft、noindex、404、query 變體排除；全站無可索引頁時仍有合法空 sitemap。

`robots.txt` 在 Build Time 依全站索引設定產生並提供 Sitemap URL。GSC 只管理可選 HTML meta verification，不延伸其他平台整合；null 時不輸出。

RSS 使用 `@astrojs/rss`，依 Published 集合、穩定排序與 maxItems 產生；noindex 不因索引設定被排除。完整日期、GUID 與隔離規則見第 13 節。

| 搜尋結果            | Browser Runtime | 搜尋及結果組合  |

## 14.2 允許的 JavaScript 行為

包括：

- 動畫、特效與轉場。
- 逐字、逐行或漸進式文字顯示。
- Navigation Menu 操作。

# 15. 媒體處理系統

## 15.1 原始來源、asset 與公開 URL

每個來源保存 `media/source/<UUID>/original.<ext>` 及 `meta.json`。來源 metadata 為 `{schemaVersion:1,id,kind,source,displayName?,posterTimeSeconds?}`；kind 為 image／video，image 不可設定 poster 時間。來源與原檔名稱不公開。

固定公開引用為 `/media/<UUID>/image.webp`、實際寬度的 `image-<width>.webp`、`video.webm`、`poster.webp`，輸出對應根 dist/media。不能使用虛構的 `/media/cover.webp`、私有 cache 路徑或來源路徑。

圖片處理另可產生 `image-social.webp`（1200 × 630 留白）與 `image-social-crop.webp`（同尺寸裁切）；SVG／ICO 與 site-icons 可產生各自受管的圖示變體。只使用媒體庫實際提供的路徑，不自行猜測檔名。啟用且完成相關圖示設定時，網站會另外輸出 `/site.webmanifest`；沒有啟用時不產生空的 Manifest。

媒體庫 DTO 為 `{id,kind,displayName,posterTimeSeconds,mimeType,byteSize,width,height,durationSeconds,sourceSha256,asset}`。尺寸是方向校正後實測；image 時間欄位為 null，video duration 必填；未完成／失效的 asset 為 null。HTTP 不回原檔位置、cache 或 inputRevision。

Node-only `inputRevision` 追原始檔＋metadata raw 版本，用於 queued 工作來源檢查；HTTP 強 ETag 額外包含 DTO／asset，處理完成可變，不能拿來當 queued 原始來源版本。sourceSha256 與 binding.sourceRevision 仍是原檔 bytes SHA-256，不混用三者。

## 15.2 固定處理 preset

| 項目       | 正式設定                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- |
| 圖片輸入   | 靜態 JPEG／PNG／WebP／AVIF 及受安全規則限制的 SVG／ICO；raster ≤25 MiB、40 MP、單邊 ≤12,000，拒絕動畫；SVG／ICO 另受專用解析界線限制                              |
| 圖片輸出   | 一般正文圖採 Sharp autoOrient→sRGB→WebP，quality80／alphaQuality100／effort4，去 metadata、保留透明、不裁切不放大；分享圖另產生留白／裁切變體 |
| 圖片尺寸   | 標準寬 min(1280,原寬)，額外 480／768／1920，只生成小於原寬且不重複標準寬的變體                                             |
| 影片輸入   | MP4／MOV／WebM，≤512 MiB、600 秒、60 fps、8.3 MP、單邊 ≤4096，需可解碼影像軌                                               |
| 影片輸出   | 校正方向，等比不放大，長邊 ≤1920／短邊 ≤1080、偶數尺寸、SAR1、yuv420p，VP9 CRF32／b:v0／good／cpu-used2／row-mt1／threads2 |
| 聲音／fps  | 第一音軌如存在則 Opus96k／雙聲道48kHz；fps=min(原有效平均fps,30)；不帶字幕／data／chapters／原 metadata                    |
| Poster     | 作者指定 0≤秒數<片長；未指定取 min(1秒,片長/2)，Sharp WebP 寬≤1280                                                         |
| 邊界／執行 | ffprobe10秒、image60秒、video30分鐘；跨程序同時2圖／1影片，取消TERM→5秒後KILL並等實際close                                 |

MiB 為 1024² bytes，MP 為十進位 pixels。原片長嚴格≤600秒；Opus／容器 padding 允許衍生片實測≤601秒，不將實際值截成600。不能同時滿足偶數尺寸及不放大的極端比例回422。HTTP 只接受已定義的 article-image／article-video／site-icons 操作，不接受任意 FFmpeg／Sharp options。

## 15.3 Cache、manifest 與完成證據

私有 cache 位於 `.alfred/media/<processingHash>/`；hash 納入原始 SHA-256、完整 preset 版本、有效 poster 時間及實際工具版本。完成須 fsync、hash 與真實解碼；損壞重建，不以 encoder exit0 或 import 成功代替驗證。

MediaManifest 為 `{schemaVersion:1,assets:[{id,kind,sourceSha256,presetVersion,tools,outputs}]}`；output 含 publicPath、mimeType、width、height、byteSize、sha256，video 另含 durationSeconds。manifest 是私有處理資料，不把完整原始 metadata 放進網站。

binding 以 source／meta raw revisions 約束目前 asset；改名稱或 poster metadata 亦失效，重新處理可重用未變 bytes 的 cache。帶 jobId 時，來源 CAS 後持久 immutable receipt 作真正完成點，再建立可重建 binding 投影；投影失敗或晚取消不逆轉成功。重啟根據 receipt 回填 Job，不靠猜測 cache 存在就宣稱完成。

## 15.4 引用、上傳與正式閉包

Studio 單檔 multipart `file` 上傳，實際解碼驗 MIME／副檔名，最多3額外欄位、每欄4KiB、parts4、總傳輸513MiB。先私有 .part，abort／超限／timeout 清理，不建立假來源。處理成功可複製 img／video HTML，含真實尺寸、srcset／sizes、alt 提示及 poster。

正文、精選圖／分享圖與固定頁使用公開 `/media/...`；預覽才映射成 `/api/v1/media/files/...`。作者已填屬性保留並驗證，缺可推導尺寸／srcset 由 Core 補，alt 不推測。

正式 Build 只從 Published、Site 設定及固定頁 mediaRefs 建立可達集合；影片展開 poster，draft-only／未引用／失敗暫存／原始來源絕不整包複製。最終 HTML 再掃所有引用，缺變體、錯型別、固定頁漏登錄都阻止提升 dist。

刪除前檢查 draft／published／設定／固定頁引用，有引用409，無引用移 trash。Range 回200／206／416，只開啟已完成受管 variant，不提供任意檔案服務。

# 17. Build Pipeline 與日常命令

## 17.1 操作介面

使用者可選擇原生配置環境或 Docker。Docker 在專案根執行 `docker compose up -d --build --wait --wait-timeout 600`，主機只需 Docker 及 Compose plugin。預設 app 使用 release target，掛載整個工作區並以非 root 執行，對主機只發布 `127.0.0.1` 的4321／5173／4322；API 始終綁容器 loopback。可直接修改主機來源，或以 `docker compose exec app bash` 進入容器編輯及測試。同一作者工作區只能有一組活動 session。Linux 主機可由 `.env` 的 `LOCAL_UID`／`LOCAL_GID` 對齊 image 帳號，不能遞迴 chown 主機內容。

release用 `node scripts/start.mjs --container` 啟動；原生CLI的 `pnpm start` 預設維持loopback。先驗session／port／權限，再在同一session lease中從暖store離線安裝固定依賴並編譯，不升級套件或覆寫作者內容。只有沒有目前網站產物時才自動首次Build；已有可驗證網站則保留，來源較新仍須明確更新網站。未知產物或未解復原不猜測初始化、不清私有狀態；修復模式只啟Studio與API，操作方式見[README](../../README.md)。啟動失敗非零，停止須等待自有子程序及原生worker結束。

content、media/source、.alfred 與 dist 保存在同一主機工作區；不得將 dist 或 .alfred 個別掛為 mountpoint，避免破壞 rename 與復原。release image 包含編輯、編譯、媒體處理及 Playwright 三瀏覽器測試環境，不依賴特定 AI 服務或外部狀態 volume。Docker 從主機檢查及建置使用 `docker compose exec app pnpm validate:content`、`docker compose exec app pnpm build`；已進入容器終端則執行下列一般命令。

## 17.2 一致快照與離線依賴

Studio Build 與 pnpm build 共用 BuildCoordinator／JobManager。初始化先復原來源與產物，再取得跨程序單 build lease；CLI 只執行自己建立的 job，busy 非零，不偷偷執行歷史 queued 工作。

取 repository writer lock，對 content（含 pages）、media/source、Core／UI、site／studio／server、scripts、根設定／manifests／lockfile／CSS 取得完整相對檔案清單與 bytes hash，建立 `.alfred/builds/<jobId>/` 不可變快照；新增／刪除亦受 revision 涵蓋。排除 Git、各層 node_modules／dist／cache／reports／.alfred。

複製後重掃確認，變更回 BUILD_INPUT_CHANGED。快照以同 lockfile 執行 frozen offline install、ignore scripts，從暖 store 建立私有 node_modules／workspace links，核對連結指向快照與 native 工具可用。缺 store 明確失敗，不改 lockfile、不向 registry 下載、不把認證／process token 傳入 worker。

## 17.3 Core、媒體與完整 HTML

1. 從快照讀 Site／taxonomy／固定頁與文章；辨識草稿，檢查 schema、日期、關聯、HTML、路由及輸出碰撞。
2. Core 產生 Published 集合、排序／分類後代聚合／Tag／分頁／TOC／Breadcrumb／SEO／搜尋與媒體閉包。
3. 實際處理可達媒體並驗 hash／解碼，建立私有 render context；每篇正文獨立保存，不把全部正文塞同一巨大 JSON。
4. Astro 讀同一私有 context，React 輸出主要 UI，BaseLayout 組 Document／CSS／SEO；static＋directory 格式生成本 job output。
5. 產生 RSS／Sitemap／robots／搜尋索引，檢查全部 HTML、連結／fragment／媒體／SEO／feeds一致性、Draft sentinel、私有檔案及 browser import graph。
6. 只有 mediaPending=false、pendingLinkChecks=0 且 report revision／fileCount 與實際一致，才進入產物提升。

私有render context以穩定根目錄及`generations/<UUID>`不可變資料目錄保存，完整寫好後單檔atomic rename發布頂層index；index保留schemaVersion1與完整原欄位，增加generation UUID，沒有此欄的舊flat格式仍可讀。不得先刪active目錄再替換。讀者從同一open handle取得index metadata及JSON，開著的舊index因路徑替換而改變ctime不代表內容改變；每個loader固定同一代讀Home／Article／List／Fixed／Search及404的所有資料與SEO，不混用SiteConfig與SiteViewModel。generation須為受限UUID，目錄與檔案維持非symlink、範圍／容量及O_NOFOLLOW守門。

真正來源失效仍原子發布invalid，新請求拒絕渲染、不以last-good兜底；已於valid時捕捉某代的在途請求可讀完該完整快照。開發session保留所有已發布代以避免清理競態，只在supervisor持dev-session lease、確認網站port及所需服務port均可用後、prepare前回收舊context，studio/server模式不清。正式Build的私有代依既有snapshot清理，不進入公開dist。

Astro開發模式的`/media/`由Root tooling adapter在Vite `apply:serve`的`configureServer`掛載Server公開的`createDevMediaMiddleware`，只提供GET／HEAD及單一bytes Range（200／206／416）。每個請求重新取得當前有效context，以`routeManifest.assets`精確路徑及`mediaManifest`輸出雙重授權，沿用`MediaService.openVariant`，送出前比對同binding輸出的path／hash／size／MIME；未知或不可達404，invalid或版本不符503，不能回退舊manifest或讓新bytes冒充舊輸出。416總大小取授權manifest，HEAD及中斷回應皆關閉stream。原始素材、草稿專用／未引用資產、私有cache及管理API不公開；原Vite fs拒絕規則保留。Root adapter使用既有Root→Server相依，設定求值時解析公開Node入口，hook才用Node原生loader載入，避免Astro關閉設定module runner後無法延後import；Site不新增Server相依或跨入server/src。正式build不執行此hook，仍由`copyReachableMedia`將可達輸出複製至dist，不新增媒體副本格式或公開cache目錄。

沒有 JSON 錯誤或 SSG exit0 仍不足以算完成；完整驗證失敗時不輸出半套根 dist。相同來源／設定／工具版本應產生一致 bytes，Build 不改文章日期。

## 17.4 可復原 dist 提升

大型 base／prepared 複製、hash、fsync 在短 writer lock 前以 artifact prepare ticket 完成；最終持 writer lock 完整重掃 live inputs 及 generation，比對本輪快照。受協調變更即使改回相同 bytes 仍由 generation 偵測；IDE 任意外部並寫不宣稱具原子防護，快照仍確保本輪不混讀。

通過後先持久 promotion intent，舊 dist rename 至私有 backup，再把完整 output rename 為根 dist；第二步失敗還原 backup。這是同檔案系統可復原兩階段切換，兩次 rename 間有短暫路徑空窗，不宣稱一次原子替換。preview 以 artifact gate 協調請求，不讀半套產物。

完整 tree digest 核對後 durable artifactCommitted，Job 才 succeeded；後續 log／通知錯誤不回滾成功。未知產物版本完整保留並要求復原；服務重啟以 journal／digest 判定，不猜測目錄存在就是成功。快照原文完成後清理、保留必要摘要與最近有效備份，未解版本不清理。

目前產物由 `GET /api/v1/artifacts/current` 讀取，Core `CurrentArtifactSchema` 契約如下：

```ts
interface CurrentArtifact {
  recoveryState: 'ready' | 'recovery-required';
  current: null | {
    digest: string;
    build: null | {
      jobId: string;
      committedAt: string;
      result: BuildResult;
    };
  };
}
```

`current=null` 表示實際沒有 dist；`current.build=null` 表示有完整樹，但無法證明來源。只有本次讀取成功、recoveryState 為 ready 且 build 非 null，才能比較其 snapshotRevision 與 workspace.revision。HTTP 失敗不能拿舊 cache 宣稱同步；最近成功 Job 只是歷史紀錄，還原 A 產物後較新的 B Job 仍成功，當前來源必須顯示 A。

Artifact gate 內掃完整樹，沿目前已提交 head 的 `preparedBuildId` 取得原 build proof，再核對 digest。新 journal 保存 `baseBuildId`／`preparedBuildId`；還原精確繼承所選版本，不把 resolution 的舊 result 當來源。相同輸出 bytes 也可能來自不同來源，不能找同 digest 的最新 Job 猜測。keep-current、未追蹤樹與缺來源證據的舊紀錄回未知；不相符或損壞 proof 不會誤報同步。pruning 只清舊的大型輸出副本，保留仍被 current／base／prepared 引用的小型 journal proof。

建置期間來源變更、取消、timeout 或內容失敗均保留舊成功 dist。查看 jobId／安全診斷修正後建立新工作；成功後以 pnpm preview 檢查正式產物。

大括號為多個實際路徑的簡記，不是字面檔名。第四篇 table-content 為 noindex，仍有五篇 HTML／RSS／搜尋資料，Sitemap 的文章只含另四篇。notes 的第二頁與 tools 第一頁皆可直接檢視；分類互不同層聚合，共同 example Tag 有四篇及兩頁。

正式成功結果為 `{outputDirectory:"dist",snapshotRevision,routeCount,fileCount,warnings}`，以 jobId 追蹤私有摘要，不回絕對路徑。pnpm preview 只服務最近成功版本，本輪失敗要清楚區別舊產物可用與新建置失敗。

## 18.1 Cloudflare 發布與驗收

Cloudflare 是完整靜態產物的託管方式，不改變文章、頁面或 Build 契約。`pnpm deploy:cloudflare` 執行正式 Build，以 ArtifactStore 的同 gate 擷取介面核對目前 head、指定 job／snapshotRevision 與 digest，固定完整副本後釋放 gate；網路傳輸不持續鎖住本機網站。

分流規則固定：`assets/**`、`media/**` 上 R2、使用原相對 key；其餘合法公開檔案上 Workers Static Assets，包含 HTML、404、搜尋 JSON、RSS、Sitemap 及 robots。兩集合互斥且完整涵蓋本次正式網站，不改 XML 副檔名、不增加 R2 讀取 handler 或 binding、不使用 SPA fallback。Worker 依指定帳戶與同名名稱建立／更新，既有其他應用設定或多版本分流拒絕覆蓋。

使用者在根 `cloudflare.config.json` 指定 `schemaVersion:1`、`accountId`、`workerName`、`bucketName`；可選 `workersPlan` 為 `free`／`paid`，預設 free，用於 20,000／100,000 靜態檔案容量預檢，單檔 25 MiB。方案宣告不是帳務核驗，實際限制以平台為準。R2 使用預設 jurisdiction 的標準 S3 endpoint、指定專用 bucket 的 Object Read & Write 憑證；bucket 先由使用者建立。根 `.env.cloudflare` 僅含 `CLOUDFLARE_API_TOKEN`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY` 三個欄位，分別提供 Worker Token 與 R2 S3 認證。兩個實際檔案皆私有 0600、不進 Git／image／公開來源包。dry-run 不讀憑證、不連遠端；Build／lifecycle 不繼承部署憑證。

R2 傳輸串流計算 hash、支援大檔 multipart；覆寫前先完成本輪全部舊檔備份，持久保存 intent／確認結果。已知未完成、未知提交、遠端衝突及可重試錯誤分開處理，不以 404 推論在途寫入必定失敗。status 只查證；restore 先核對全部物件、備份與可回復版本，再先 R2、後 Worker。保留成功新 key 與舊資源，不自動清 bucket 或 CDN。單一發布者是前提；固定 key 覆寫可能先影響舊網站，R2／Worker／CDN 不構成全站原子交易。

副本、manifest、journal、receipt 與 R2 覆寫備份保存在私有 `.alfred/deployments/<deploymentId>/`，以 UUID 追蹤，時間存 UTC。`uploadStatus` 與 `domainVerification` 分開；上傳與版本證據不代替正式公開 HTTP 結果。網域、公開 R2 來源、Cloud Connector、Worker Routes、HTTPS 與快取由使用者初次設定。明確收到設定完成與 domain 後才驗網站、原路徑／MIME、影片 Range、SEO、快取與三瀏覽器；分流及規則保留另有控制台人工查證，不以回應標頭推定通過。原生與 Docker 使用同一命令與設定，完整初次操作見[Cloudflare 部署](../deployment/Cloudflare部署.md)。

# 19. 效能、安全性與內容品質

## 19.1 效能

網站以低 JavaScript 負載、低資源請求與快速初始顯示為設計原則。

- 主要內容完整預渲染。
- 不使用公開網站的動態內容 API。
- React 展示元件預設不需要 Hydration。
- 互動 JavaScript 按功能載入。
- 圖片使用本地最佳化及 Responsive Images。
- 影音採用處理後的靜態資源。
- HTML、CSS、JS 及媒體適當支援快取。

## 19.2 SEO 品質

所有正式可索引頁面必須具備完整 HTML 及必要 Metadata。

Category 與 Tag 分頁使用正常 Anchor 連結，讓搜尋引擎能發現後續內容。

Canonical、Breadcrumb、Sitemap 與正式 URL 使用相同的 Core Routing 規則。

## 19.3 內容一致性

Article 是所有公開文章資料的唯一來源。

Category、Tag、TOC、搜尋索引、RSS 及 Sitemap 均根據相同內容資料產生。

不應分別維護多份互相獨立的文章列表。

## 19.4 本機安全性

Node.js Local Service 僅供本機使用，預設不對外提供網路服務。

檔案操作應限制在允許的專案目錄，避免路徑穿越與任意檔案存取。

Build 相關操作應透過固定指令執行，不接受任意命令輸入。

## 19.5 HTML 內容信任模型

Article HTML 由可信任的本機作者維護。

系統可以將文章 HTML 作為可信任內容進行 Build-Time Render，但須驗證必要的結構與資源引用。

如果未來引入不受信任的 HTML 來源，則必須另外設計內容清理及安全隔離機制。

## 19.6 公開網站安全邊界

正式網站不部署：

- Node.js Service。
- React Studio。
- 使用者管理 API。
- CMS Database。
- PHP。
- SSR Server。

公開網站仍需留意第三方 JavaScript、前端依賴套件及實際部署環境的安全設定。

# 21. 最終架構定義

本系統正式採用：

**Node.js + TypeScript Core + React Studio / Shared UI + Astro SSG + HTML Content + JSON Metadata**

各模組的核心責任如下：

| 模組            | 最終責任                                     |
| --------------- | -------------------------------------------- |
| Node.js         | 本機執行環境、檔案操作、管理服務及建置流程   |
| Content         | 保存文章 HTML、Metadata 與網站設定           |
| TypeScript Core | 統一資料模型、路由規則、內容驗證與處理邏輯   |
| React           | 共用網站元件、本機編輯、管理與預覽           |
| Astro           | 靜態路由列舉、頁面模板、預渲染及靜態資源建置 |
| Static Output   | 提供不依賴動態後端的完整公開網站             |

**系統的基本執行模式為：**

1. 使用者選擇原生環境或 Docker，自行或透過 AI 調整首頁、FAQ、About 等固定頁、共用文章版型及網站設定。
2. 日常透過 Studio 或 IDE／AI 編輯 HTML 與 Metadata、管理媒體；新增文章不新增 React／Astro 元件。
3. Node.js 提供本機檔案操作及來源預覽；TypeScript Core 統一處理資料模型、Category、Tag、Routing、TOC、Pagination 與 SEO。
4. 在4321檢查目前來源；明確 Build 後，Astro 依 Core 資料與 React 展示元件產生完整靜態 HTML，並產生 RSS、Sitemap、搜尋索引及最佳化媒體。
5. 全部檢查通過後更新完整 `dist/`，在4322確認最近成功網站，作為唯一網站交付產物。
6. 要發布 Cloudflare 時，以明確指令將本次正式產物分流至 Workers Static Assets 與 R2；完成初次網域設定後另驗正式網址。本機成功建置與公開網站驗收分開。

**最終設計原則：網站的內容、資料模型與路由規則獨立於 SSG；開發和管理依賴 Node.js 與 React，公開網站則只依賴已產生的靜態檔案。**

除了文章總覽／搜尋頁的前端查詢狀態，所有主要內容都在建置時完成預渲染。React 可以負責元件與互動，但不能成為一般頁面主要內容出現的必要條件。

本規格定義目前的資料與操作契約。具體工作方式見[新增文章流程](新增文章流程.md)與[一般獨立頁面建立流程](一般獨立頁面建立流程.md)；執行、備份與開發入口見[README](../../README.md)。
