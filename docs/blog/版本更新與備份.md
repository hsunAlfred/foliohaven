# 版本更新與備份

這個系統允許直接修改原始碼，因此你的網站包含兩部分：**自己的程式修改**及**文章、設定與媒體等作者資料**。更新系統時要同時保留兩者，不能把新版壓縮檔整包蓋在目前專案上。

## 0. 版本相容性

### 私有資料與識別命名相容規則

私有資料預設使用 `.foliohaven/`。本文後續路徑以此名稱示範，舊專案依下列規則選擇實際目錄，不需要為了配合文件搬移資料。

| 目錄狀態 | 使用方式 |
| --- | --- |
| 兩者都不存在 | 建立並使用 `.foliohaven/` |
| 只有 `.foliohaven/` | 使用 `.foliohaven/` |
| 只有 `.alfred/` | 繼續使用 `.alfred/` |
| 兩者同時存在 | 只使用 `.foliohaven/`；舊目錄不讀寫、不合併、不刪除 |

新目錄存在但權限錯誤、是符號連結或資料損壞時報錯，不回退舊資料。工作持有程序鎖時，變更私有根會以 `PRIVATE_DIRECTORY_CHANGED` 停止操作；先保存並停止所有服務、建置與部署，再調整目錄。備份及還原保留實際目錄名稱；兩根並存時也保留未使用的舊根，不把兩套交易或部署紀錄混在一起。

內部識別採以下相容規則，一般使用不必手動設定：

- 環境變數使用 `FOLIOHAVEN_RENDER_CONTEXT`（呈現資料位置）、`FOLIOHAVEN_RENDER_OUTPUT`（網站輸出位置）、`FOLIOHAVEN_SNAPSHOT_REVISION`（來源快照雜湊）、`FOLIOHAVEN_RELEASE_VERSION`（容器版本）。同後綴的 `ALFRED_*` 只在新名稱未設定時讀取；新值即使是空字串仍優先，無效時報錯，不回退舊值。新程式只產生新名稱。
- 本機服務使用 `x-foliohaven-process-token`、`x-foliohaven-studio-origin`、`x-foliohaven-editor-id`，兼容對應的 `x-alfred-*`。新舊值一致可接受；值衝突或同名重複一律拒絕，保留原本的驗證與來源檢查。
- Cloudflare 新部署訊息為 `foliohaven deploy <UUID>`／`foliohaven restore <UUID>`，仍辨識舊 `alfred-wiki` 訊息。R2 新 metadata 為 `foliohaven-sha256`、`foliohaven-byte-size`、`foliohaven-deployment-id`，仍辨識完整的 `alfred-*` 舊組；雙組並存必須完整一致，不混搭，也不以舊組掩蓋無效的新組。既有物件不為改名批次重傳；真正更新時才寫新格式，還原保留備份的原始 metadata。

相容方向是新版讀取舊資料與舊請求，不表示舊版程式能處理新版產生的全部識別。回退時配對還原程式與完整備份，不只退 Git，也不直接改寫 journal、快照或部署指紋。

### 由 1.0.0 升級至 1.1.0

1.1.0 延續原有文章及網站設定資料模型，重點為識別相容、驗證與 Docker 工具鏈，以及共通操作指南。依下方完整備份與副本流程升級，保留自己的文章、媒體、自訂程式及部署設定。

- **保留實際私有根**：只有 `.alfred/` 時繼續沿用；不必搬移，也不要為了配合文件先建立空的 `.foliohaven/`。若兩根已並存，新版只使用 `.foliohaven/`，須先確認其中有完整且配對的作者工作與復原資料，舊根保留、不合併。選定根或新識別不合法時，修正該問題，不以舊根／舊值回退掩蓋。
- **更新容器版本並重新建置**：若自己的 `.env` 設有 `RELEASE_VERSION`，改為 `1.1.0`。保留原本的 UID／GID、連接埠及私有值，以新版 Dockerfile 建立 image；新版提早對齊擁有者並重用工具鏈，不需要遞迴放寬作者目錄的權限。原生使用者依新版 README 完成 frozen 安裝。
- **區分日常快檢與升級驗收**：可在整合自己的修改時使用 `pnpm verify:quick`；它不取代第 3 節的完整驗證。完整 `pnpm verify` 會按實際剩餘記憶體限制併行，保留全部整合與三瀏覽器測試；正式發行另須最終公開來源的完整資格。
- **核對設定及頁面品質**：新增的[網站開發與品質標準](網站開發與品質標準.md)及[SEO 設定與繼承](SEO設定與繼承.md)集中說明既有能力與驗收方式，保留作者明確設定；PageSpeed 目標另行量測，不以測試通過推定分數達標。
- **保留 Cloudflare 復原證據**：不需要因識別改名重新建立 Worker 或 R2 bucket。舊部署訊息、metadata、journal 與備份繼續由相容規則判讀，不手動改名或改寫指紋；真正發布及還原依原有受控流程操作，不能用本機升級代替雲端驗收。

若需回復 1.0.0，停止新版並還原升級前同一份完整備份及原程式／工具版本。1.0.0 不保證能使用新版產生的識別或工作紀錄；只有 `content/` 或切回舊程式都不足以完整回復。

以下兩節保留特定歷史版本的升級行為；更新其他版本時，另核對對應版本的 CHANGELOG 與相容性說明。

### 由 0.3.1 升級至 1.0.0

1.0.0 沿用 0.3.1 的程式行為與資料格式，無須另做資料轉換。保留自己的文章、媒體、自訂頁面、版型及 Cloudflare 設定，依下方流程先備份，再在副本完成驗證。若自己的 `.env` 已設定 `RELEASE_VERSION`，將它更新為 `1.0.0`，其餘個人設定保留。

### 早期版本：升級到 Foliohaven 0.3.0

0.3.0 可讀取原 0.2.0 的文章、設定及媒體資料；未填的新欄位套用預設值，原有單筆 SEO、文章網址及媒體 URL 保留。套件名稱改為 `@foliohaven/*`，自訂程式中的舊 imports 與 `pnpm --filter` 必須一起更新；Docker 內部工作路徑與 image 名稱也改用新名稱，請比較自己的 Compose 覆寫設定。

保存文章或設定後，新版可能寫出摘要、延伸閱讀、頁型 SEO、分享圖來源及圖示欄位。舊版的嚴格 Schema 不接受這些新欄位，因此降版必須還原升級前完整備份及原程式版本；只 checkout 舊程式不足以還原。`.alfred/` 工作、復原及部署紀錄與既有 Cloudflare 資源識別仍保留相容性，不需要為產品改名重新命名或清空它們。

## 1. 停止後備份完整專案

1. 保存 Studio／IDE 尚未保存的內容，等媒體處理、網站更新與 Cloudflare 發布／還原工作結束；結果未知時先保留紀錄並查詢狀態。
2. Docker 執行 `docker compose down`；原生環境以 Ctrl-C 停止自己的作者服務及預覽。確認沒有另一個 IDE／AI 同時修改。
3. 將完整專案複製到專案以外的私有位置並保留權限，記下根 `package.json` 的版本。備份不加入 Git、image 或公開網站。

完整備份至少涵蓋下列資料；保存整份專案可降低遺漏自訂檔案的風險。

| 項目                                                                  | 保存原因                                                                     |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `content/`                                                            | 自己的文章、網站設定、分類、Tag 與固定頁 JSON                                |
| `media/source/`                                                       | 原始圖片、影片與媒體設定                                                     |
| 自訂程式及資源                                                        | 首頁、固定頁、文章版型、Header／Footer、CSS、Astro 入口、registry 及其他修改 |
| `.foliohaven/`、`dist/`                                                   | 交易、工作與復原證據，以及對應的成功網站                                     |
| `package.json`、workspace manifests、lockfile、工具與容器設定         | 還原同一版本及相依套件所需資料                                               |
| 自己的 `.env`、`cloudflare.config.json`、`.env.cloudflare` 等本機設定 | 連接埠、UID／GID、Cloudflare 部署目標與憑證；含私密值時更應妥善保護          |

Git 可保存自己的原始碼修改，但不取代作者資料與 `.foliohaven/` 的完整備份。只有 `dist/` 也不足以恢復可編輯的網站；Studio 內的版本及垃圾桶同樣不能代替外部備份。

使用 Cloudflare 時，`.foliohaven/deployments/<UUID>/` 包含固定網站副本、上傳紀錄與 `backups/r2/` 覆寫前備份；缺少它可能無法還原舊媒體。根 `cloudflare.config.json` 與 `.env.cloudflare` 也需帶入私有備份，保留 0600 與帳號擁有權。R2 中的物件與 CDN 快取不屬於本機備份，不會因換回舊專案就自動回復。

## 2. 在另一份目錄準備新版

1. 閱讀新版 [CHANGELOG](../../CHANGELOG.md) 及使用要求，確認版本、工具鏈、資料格式與必要轉換。若新版本宣告不相容且沒有可用轉換方式，先保留舊版，不直接嘗試覆蓋。
2. 把新版放到另一個目錄，保留舊專案與備份。將自己相對於舊版的程式修改，逐項比較並套用到新版；特別檢查共用元件、樣式、固定頁入口、registry 及自訂 Schema。
3. 在兩邊服務都停止的狀態下，帶入同一份備份的 `content/`、`media/source/`、`.foliohaven/`、`dist/` 及需要的私有設定；取代新版隨附範例，不把兩套文章及交易資料混在一起。保留自己的 `content/site.json`，尤其正式網站網址 `siteUrl`，不要以新版中性範例覆蓋。若版本需要轉換，依該版指示操作並保留轉換前備份。
4. 檢查 `.env` 與新版 `.env.example` 的差異，保留自己的值並補齊新增設定。新版套件與 lockfile 以新版為準；不要把舊 lockfile 蓋回去來繞過相依問題。自訂依賴需重新核對相容性。
5. 使用 Cloudflare 時，另比較 `cloudflare.config.example.json`、`.env.cloudflare.example` 與[部署文件](../deployment/Cloudflare部署.md)，保留自己的目標與憑證；不要以範例覆蓋實際檔案。新舊副本不要同時對同一 bucket 發布，本機鎖不能協調不同副本或不同主機。

可讓 AI 協助比較新舊程式，但先要求它閱讀 AGENTS.md，列明哪些是自己的修改，並保護作者資料。不要讓工具只根據同名檔案決定覆蓋。

## 3. 啟動並檢查新版副本

Docker 依新版 README 重新建立對應 image；`.env` 如有 `RELEASE_VERSION`，需與新版根 `package.json` 一致。原生環境切換到新版要求的 Node.js／pnpm，再做 frozen 安裝及環境檢查。

舊工作階段已停止後，才能啟動新版副本。即使使用不同連接埠，也不要讓兩套服務同時操作同一份作者目錄。`.foliohaven/` 與 `dist/` 保持在專案所在檔案系統中，不各自掛成獨立 mountpoint。

```bash
pnpm run setup
pnpm typecheck
pnpm validate:content
pnpm verify
```

原生環境先停止新版副本的作者服務，再執行上述檢查；整合及完整驗證會使用 4321／5173／3001。Docker 的完整驗證改用一次性容器，不在活動中的 app 內執行：

```bash
docker compose stop app repair
docker compose run --rm --no-deps app pnpm verify
```

驗證成功後再 `docker compose up -d --wait --wait-timeout 600 app`。完整 `verify` 包含工具檢查、型別、內容建置及測試；任何必要檢查失敗，先查明原因，不刪除測試或私有紀錄來換取通過。

再人工檢查 Studio 可讀取自己的文章與設定、`4321` 的自訂頁面與版型，以及 `4322` 成功產物的文章、導覽、圖片、影片與 SEO。確認後才採用新版專案並重新交付完整 `dist/`。建置成功不會自動部署公開網站。

副本驗收也需依[網站開發與品質標準](網站開發與品質標準.md)及[SEO 設定與繼承](SEO設定與繼承.md)，以升級前成功網站及留存結果為基準，核對 SEO 繼承與輸出、媒體、閱讀位置、目錄、鍵盤操作及既有互動是否退步。效能比較採相同頁型、內容、視窗、工具與裝置／網路條件，記錄差異與未測範圍；先完成副本可驗項目，正式網域的 PageSpeed、資源與快取品質於明確部署後另行驗收，不以本機結果宣稱正式站已通過。

Cloudflare 使用者再執行 `pnpm deploy:cloudflare --dry-run` 檢查新版部署入口；真正發布與正式網址驗證依[Cloudflare 部署](../deployment/Cloudflare部署.md)操作。既有網域規則通常可沿用，仍需核對發布前後與可變媒體的公開結果。

## 4. 失敗時保留現況並復原

- 新版相容或程式檢查失敗：停止新版，保留失敗副本與診斷，使用未修改的舊專案及對應環境繼續工作。不要把新版修改過的資料直接混回舊版。
- 來源或產物處於待復原狀態：依 README 啟動修復模式，在 Studio「衝突與復原」比較版本並明確選擇；不手工清空 `.foliohaven/` 或覆蓋 `dist/`。
- 需要外部備份還原：先停止服務並另外保存目前專案，再還原**同一份完整備份**及其對應程式版本、工具鏈與權限；不要拼接不同時間的文章、媒體、交易資料及產物。
- Cloudflare 發布失敗或結果未知：先用該次 `deploymentId` 查詢，不把本機回到舊版當成雲端也已回復。明確還原需有對應紀錄、R2 備份與仍可回復的 Worker 舊版本；完成後另驗證公開網址與 CDN。不要刪除部署紀錄來略過衝突。

平時只改文章、頁面或 CSS，不需每次重做容器。更動依賴、工具鏈或容器設定後，才依對應版本重建；公開網站仍以重新建置的完整 `dist/` 更新。
