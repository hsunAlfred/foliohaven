# 一般獨立頁面建立流程（Static Page Workflow）

本流程適用於首頁、FAQ、About、Privacy 等具有獨立 URL 與 React 主體的固定頁面。首次架站可先完成這些頁面，再依[版型與樣式調整](版型與樣式調整.md)決定共用文章版型。新增文章請使用[新增文章流程](新增文章流程.md)，不要為每篇文章建立固定頁。

固定頁由 React 負責主要 UI，Astro 負責入口、Document、SEO 及 SSG；Core 統一管理路由與 SEO。每個固定頁同時具備 **React 元件、公開 export、Astro Entry、fixedPages 登錄**。若使用 JSON 設定，再加上該頁 `pageSchemas` 登錄。

以下以 `/about/` 為可直接採用的完整範例，最終輸出 `dist/about/index.html`。範例不會自動新增到目前網站。

## 1. 實際檔案與職責

| 路徑                                | 用途                                                               |
| ----------------------------------- | ------------------------------------------------------------------ |
| `packages/ui/src/pages/`            | React 頁面主體；既有 home／category／tag／articles／not-found      |
| `packages/ui/src/index.ts`          | `@foliohaven/ui` 公開出口；跨套件不得直接匯入 src                 |
| `packages/ui/src/components/`       | SiteHeader、SiteFooter、Navigation、Breadcrumb 等共用展示元件      |
| `packages/ui/src/styles/index.css`  | 共用樣式來源；build／watch 同步至公開 `@foliohaven/ui/styles.css` |
| `site/src/fixed-pages.ts`           | 唯一固定頁 URL／Entry／SEO／mediaRefs／pageSchemas 登錄            |
| `site/src/pages/`                   | Astro 頁面入口                                                     |
| `site/src/lib/server/context.ts`    | `loadFixedPage` 等私有 render context 讀取介面                     |
| `site/src/layouts/BaseLayout.astro` | HTML Document、共用 Header／Footer、CSS 及 SeoHead                 |
| `site/src/components/SeoHead.astro` | Core SeoViewModel 的 Head 輸出                                     |
| `content/site.json`                 | 全站設定及導覽                                                     |
| `content/pages/<pageId>.json`       | 有設定需求的固定頁資料；需逐頁 strict schema                       |

目前 `/`、`/articles/`、`/category/` 與 `/tag/` 登錄為固定入口；About／Privacy 是新增範例，不是既有頁面。TOC 在 `packages/core/src/html/`，共用 CSS 不在 `site/src/styles/`。

先依[README](../../README.md)選擇原生環境或 Docker 啟動。原生環境直接編輯來源；Docker 可編輯主機掛載的專案，或以 `docker compose exec app bash` 進入容器，使用編輯器或連入容器的 IDE／AI 工具。以下 `pnpm` 指令在原生環境、容器終端或選用的 Dev Container 中直接執行；從主機操作 Docker 時，加上 `docker compose exec app` 前綴。

## 2. Step 1：定義 URL、資料與 SEO

本例約定：

- pageId：`about`，只作固定頁識別。
- URL：`/about/`，必須帶尾斜線。
- React：`packages/ui/src/pages/about/AboutPage.tsx`。
- Entry：`site/src/pages/about/index.astro`。
- JSON：`content/pages/about.json`。
- SEO：獨立標題／描述，其餘繼承全站。

確認 URL 不與其他固定頁、文章、分類／Tag 或保留資源衝突；Core 與 Astro adapter 會共同檢查完整路由及輸出檔案碰撞，不能只檢查有沒有同名 Astro 檔。

以 IDE 修改來源時，先在 Studio 頂部「工作區」選單切換 IDE 模式，避免同時由 Studio 保存 `content/site.json` 等檔案。Studio 桌面從左側導覽進入功能，窄螢幕以「開啟導覽」展開。固定頁的 React、Astro、registry 及頁面專用 JSON 都由 IDE 維護；Studio 文章編輯器不會列出或編輯目前瀏覽的固定頁。

## 3. Step 2：建立 React 頁面並公開匯出

建立 `packages/ui/src/pages/about/AboutPage.tsx`：

```tsx
export interface AboutPageProps {
  readonly headline: string;
  readonly introduction: string;
}

export function AboutPage({ headline, introduction }: AboutPageProps) {
  return (
    <main id="ui-main" className="page-container about-page" tabIndex={-1}>
      <h1>{headline}</h1>
      <p>{introduction}</p>
      <p>
        <a href="/articles/">瀏覽文章</a>
      </p>
    </main>
  );
}
```

在 `packages/ui/src/index.ts` 增加：

```ts
export * from './pages/about/AboutPage.js';
```

這裡使用 `.js` specifier，沿用 NodeNext／ESM 編譯規則。Astro 應從 `@foliohaven/ui` 匯入，不使用相對路徑跨入 UI src。

頁面只輸出一個 `main#ui-main` 與 H1；Header／Footer 已由 BaseLayout 放置，不在頁面重複包一層。文字 Props 使用正常 React escaping；UI 不讀檔、不呼叫 Node API、不自行計算全站路由或 SEO。

## 4. Step 3：建立 JSON 與同一份 strict Schema

建立 `content/pages/about.json`：

```json
{
  "headline": "關於這個網站",
  "introduction": "這裡記錄以 HTML 與 JSON 維護的文章與實作筆記。"
}
```

在現有 `site/src/fixed-pages.ts`，將原本僅供型別的 Zod 匯入：

```ts
import type { z } from 'zod';
```

改成可執行的匯入：

```ts
import { z } from 'zod';
```

在同檔定義並匯出 schema，取代原本空的 `pageSchemas`，保留其他既有程式：

```ts
export const aboutPageDataSchema = z.strictObject({
  headline: z.string().trim().min(1).max(200),
  introduction: z.string().trim().min(1).max(2000),
});

export const pageSchemas: Readonly<Record<string, z.ZodType<JsonValue>>> = {
  about: aboutPageDataSchema,
};
```

`JsonValue` 已由同檔從 Core 匯入。若已有其他頁面 schema，將 `about` 合併進原有物件，不要覆蓋其登錄。

pageId 為 1–80 字元 lowercase kebab-case；JSON 為 UTF-8，每檔最多 256 KiB。未登錄、未知欄位、錯誤型別或超限都明確失敗，不回退成空頁。`pageSchemas` 與 fixedPages 一起編譯至 `@foliohaven/site/registry`，Node／snapshot 使用同一公開設定，不另存一份 JSON registry。

如果內容完全由 JSX 維護，可省略本步 JSON 與 schema；下步改為直接傳入 JSX 固定內容。不要建立沒有 schema 的 `content/pages/about.json`。

## 5. Step 4：登錄固定頁與媒體

在 `site/src/fixed-pages.ts` 的 `fixedPages` 陣列加入下列項目，保留既有 home／articles／category-index／tag-index：

```ts
FixedPageSchema.parse({
  id: 'about',
  path: '/about/',
  entry: 'src/pages/about/index.astro',
  seo: {
    title: '關於這個網站',
    description: '說明網站內容、寫作方式與資料維護原則。',
    index: null,
    ogImage: null,
  },
  mediaRefs: [],
}),
```

`entry` 相對於 `site/`，不是 repository 根；對應 Astro 檔案必須存在且能對應登錄 URL。未登錄固定 Entry、重複 URL、symlink、被 Astro 忽略的 `_`／隱藏 Entry 等會拒絕建置。動態文章／分類／Tag、輔助 endpoint 與 404 由明列例外處理，不能拿來繞過固定頁登錄。

`seo` 接受 `{title,description,index,ogImage,imageSource}`；文字與索引欄位可為 `null` 表示繼承，`imageSource` 為 inherit／custom／none；`ogImage` 只能使用受管圖片路徑，不能隨意增加 canonical 等未知欄位。Core 依 path 建立 canonical，固定頁預設 `og:type=website`，不產生文章 BlogPosting。

若頁面或該頁使用的共用 UI 引用受管圖片／影片，把完整公開路徑加入 `mediaRefs`；例如 `/media/<實際UUID>/image.webp`。分享圖也必須可處理輸出。先在 Studio「媒體庫」按「上傳媒體」，點縮圖網格開啟「媒體設定與引用」，必要時保存設定後按「處理媒體」。處理完成才會提供可複製的公開路徑及 HTML；影片也會提供 Poster。使用真實路徑，不把範例 placeholder、原檔路徑或預覽 API URL 當作正式引用。

固定頁的獨立 `seo.ogImage` 仍在本節 registry 透過 IDE 設定；Studio 不提供固定頁專用 SEO 表單。需要全站共用分享圖時，可在完成 IDE 編輯並切回 Studio 模式後，進「全站設定」→「SEO 與社群分享」的「Default Social Image」，開啟選圖彈窗，搜尋並選擇圖片或影片封面，再選尺寸、按「使用這個尺寸」，最後「保存全站設定」。同一媒體的多種尺寸先合併顯示，點選後才選尺寸；不需在不同尺寸卡片中辨認同一張圖。自訂固定頁的 `ogImage: null` 依 Core 規則繼承全站預設；首頁、文章總覽、分類總覽與 Tag 總覽會先套用對應頁型設定。Studio 可查看當前全站分享圖及預設值；固定頁自己的 SEO 結果仍依本節 registry 及實際建置輸出確認，不能把文章編輯器預覽當成固定頁編輯器。選「不設定全站預設圖片」表示不設定全站分享圖；分享圖建議 1200 × 630，圖片處理另提供裁切及留白變體，可依用途選取；一般正文圖片保留原比例。

正式 Build 只輸出 published、全站設定及固定頁可達媒體。漏登錄而出現在最終 HTML 的媒體會在產物檢查失敗，不能靠手工複製原始檔繞過。

## 6. Step 5：建立 Astro Entry 並使用 BaseLayout

建立 `site/src/pages/about/index.astro`：

```astro
---
import { AboutPage } from '@foliohaven/ui';
import { aboutPageDataSchema } from '@foliohaven/site/registry';
import BaseLayout from '../../layouts/BaseLayout.astro';
import { loadFixedPage } from '../../lib/server/context.js';

const model = await loadFixedPage('about');
const data = aboutPageDataSchema.parse(model.data);
---

<BaseLayout site={model.site} seo={model.seo} currentPath="/about/">
  <AboutPage headline={data.headline} introduction={data.introduction} />
</BaseLayout>
```

`loadFixedPage` 讀取已驗證、由本次來源快照產生的私有 render context，回傳 `{site,seo,data}`；不在 Entry 重新讀 live content。此處重用同一個已公開 schema 取得安全型別，不建立另一套規則。React 沒有 `client:*`，主要內容於建置時完整渲染。

沒有 JSON 的頁面仍使用 `loadFixedPage('about')` 取得 site／seo，只把 React 所需文字改成固定 JSX／Props；未使用的 schema 匯入一併省略。

BaseLayout 已處理 HTML Document、language、viewport、共享 CSS、React SiteHeader／SiteFooter 與 SeoHead。不要重複輸出 `<html>`、SEO Head 或 Header／Footer。SEO 會產生 title、description、canonical、robots、Open Graph、Twitter card、適用的 JSON-LD、RSS discovery；GSC 只在首頁且有設定時輸出。404／預覽固定 noindex，規則由 Core 管理。

## 7. Step 6：接入導覽與共用樣式

若希望主導覽顯示本頁，在 `content/site.json` 的 navigation 陣列加入：

```json
{ "label": "關於", "href": "/about/" }
```

保留其他設定及導覽，整體最多 20 項。請在 Entry／registry 完整後再加入，避免暫時存在指向未知路由的設定。

也可先結束 IDE 編輯、切回 Studio 並重新讀取資料，再從「全站設定」的「導覽」加入名稱及連結，按「保存全站設定」。不要同時以 IDE 與 Studio 保存網站設定；不論採哪個入口，保存後仍須成功 Build 才會更新 `dist`。

樣式編輯 `packages/ui/src/styles/index.css`。本例使用既有 `page-container`，需要時可加入 `.about-page` 規則。Astro／預覽均匯入 `@foliohaven/ui/styles.css`；build／watch 負責複製 CSS，不直接編輯 `packages/ui/dist/`。

## 8. Step 7：開發、檢查與完整 Build

Docker app 或原生 `pnpm start` 已提供 `4321`，保存 React／CSS／registry 後檢查更新。若要只啟動網站開發，先停止原工作階段，再執行：

```bash
pnpm dev:site
```

同時需要 Studio、模式切換或媒體庫時改用 `pnpm dev`，不要兩套指令同時占用相同固定 port。Astro 為 `4321`，Studio 為 `5173`，原生直接開啟 localhost 網址；選用 Dev Container 時可用編輯器的連接埠轉送。`pnpm dev:site` 會啟動必要 package build／watch 及私有呈現資料刷新，不必直接啟動裸 Astro。

開啟 `/about/`，檢查 H1、導覽、文字、鍵盤 focus、手機寬度及媒體。固定頁請使用瀏覽器的響應式檢視工具；Studio 的桌機／平板／手機模擬及「放大預覽」專供文章，不會載入這個固定頁。日常 React／CSS／HTML／JSON 修改使用 watch，不需重建容器。新增 registry 的編譯設定亦由 package watch 更新；若開發程序已停止，重新執行命令會先編譯。

完成後，在 Docker 模式依序執行：

```bash
docker compose exec app pnpm typecheck
docker compose exec app pnpm validate:content
docker compose exec app pnpm build
```

Docker app 或原生 `pnpm start` 已提供 `4322`，成功後重新整理檢查。原生與容器內使用相同三個 `pnpm` 指令；若以 `pnpm dev` 或 `pnpm dev:site` 啟動，另開終端執行 `pnpm preview`，不要重複啟動已有的預覽服務。

- typecheck 包含公開 library 型別、Node／browser TypeScript 與 Astro check。
- validate:content 檢查來源、registry、路由與實際媒體；可能列出待最終 HTML 檢查的固定頁 fragment，不產生根 dist。
- build 使用唯一正式 orchestrator，從一致快照完成媒體、React／Astro、完整 HTML／錨點／SEO／輔助檔與私有資料隔離檢查，成功才替換根 dist。不要直接用 `astro build` 當正式完成。
- `4322` 預覽只服務最近成功產物；檢查 `/about/` 對應 `dist/about/index.html`，不是 Astro 開發版。

停用瀏覽器 JavaScript 仍必須看到主要內容。目前 hydration 只接受既有 `/articles/` 搜尋 island，其他頁面任意新增 `client:*` 會被產物檢查拒絕；本例不新增 hydration。若需要獨立 JavaScript 增強互動，仍須保持完整預渲染內容、資源與 bundle 安全邊界；若改變 hydration 契約，須同步規格及 renderer 驗證，不能只加 `client:load`。

## 9. 失敗、變更與復原

| 情況                                      | 處理方式                                                                |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| 未登錄 Entry／pageSchema、缺 JSON／壞欄位 | 依安全診斷補齊同一份 registry 與資料，再重跑檢查                        |
| URL／輸出路徑碰撞、導航／fragment 無效    | 更正入口或引用；不能讓 Astro 自己選一個輸出                             |
| 媒體缺漏／未登錄／處理失敗                | 修正 mediaRefs 及公開引用，等待真實處理通過                             |
| Build 期間來源變更                        | 本輪不提升，舊 dist 保留；停止修改後重新建立 Build                      |
| 未完成來源／dist 復原                     | 開啟 Studio「衝突與復原」，比較版本並明確處理；不要手工清空 .alfred     |
| 本輪 Build 失敗                           | 舊成功產物仍可預覽；修正後重新 Build，不能把 dev 頁面視為公開產物已更新 |

Studio 的「網站更新與工作」可按「更新網站」，並以表格列出工作，點紀錄開啟「工作詳細資料」查看階段、診斷及安全錯誤；「衝突與復原」點「比較版本」開啟「復原比較」，逐一查看或下載版本後再明確決策。這些彈窗管理工作與版本，不會取代固定頁的 IDE 編輯流程。

既有頁面改 URL 時，同步 Entry、registry、導覽及所有站內連結；不自動建立 redirect。刪除固定頁時，同步移除 Entry、登錄、專用 JSON／schema、公開 export（若不再使用）及導覽／其他引用，再成功 Build 才從 dist 移除。

文件範例依目前公開入口與 Schema 維護，整體架構見[主規格](<全靜態部落格系統 — 需求與技術架構規格 v1.0.md>)；啟動、備份與修復模式見[README](../../README.md)。
